# DEC-04 是否引入 Kafka（Phase 3）

**结论：Phase 3 暂不引入 Kafka，维持 PostgreSQL outbox + polling dispatcher。**

## 决策依据

1. 当前事件链路主要为知识入库与索引推进，消费者数量与吞吐仍在单数据库可控范围内。
2. 现有 outbox 已具备可追踪性与重试语义，能满足 Phase 3 的在线评估与能力报告场景。
3. 引入 Kafka 将显著增加运维面（集群、分区、副本、监控、回放策略），不符合当前阶段成本收益比。

## 触发重评估的阈值

任一条件满足时，重新评估是否迁移 Kafka：

- 峰值事件吞吐持续超过 **200 msg/s** 且 outbox 延迟超过 **5s**。
- 消费者扩展到 **3 类以上独立下游**（例如通知、画像、外部同步）并要求独立回放。
- 单库 polling 对在线查询造成显著抖动（p95 延迟恶化 > 20%）。

## 迁移预留

- 继续保持领域事件 payload 版本化。
- 业务代码仅依赖发布接口，不绑定传输实现。
- 保留 outbox 表可作为 Kafka bridge 的 source，不影响现有事务边界。
